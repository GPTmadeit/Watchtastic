# Contributing to Watchtastic

Thanks for considering it. This document covers how to get a build running and the few
rules that exist because breaking them causes real damage to someone's radio.

## Getting set up

You need **JDK 17** and the **Android SDK with API 36**. Android Studio installs both.

```bash
git clone https://github.com/GPTmadeit/Watchtastic.git
cd Watchtastic
./gradlew testDebugUnitTest   # ~26 tests, no device needed
./gradlew assembleDebug
```

The debug APK is signed with Android's standard debug key and installs immediately. The
release variant needs signing material you won't have — see [docs/RELEASING.md](docs/RELEASING.md).
You do not need it to contribute.

`local.properties` is generated by Android Studio and is gitignored. If you build from
the command line without it, set `ANDROID_HOME` instead.

## Running it

On an emulator: create a **Wear OS** AVD (API 33+) in Android Studio's Device Manager.
Everything except Bluetooth works there — you can seed the app with fake mesh data by
pushing a JSON snapshot:

```bash
adb shell run-as com.watchtastic.debug \
  sh -c 'cat > /data/data/com.watchtastic.debug/files/mesh-store.json' < your-snapshot.json
```

On a real watch, [WatchPush](https://github.com/GPTmadeit/WatchPush) installs from your
phone without a computer.

## Before you open a PR

```bash
./gradlew testDebugUnitTest lintDebug assembleDebug
```

All three must pass. CI runs exactly these on every pull request.

There is no separate formatter step — the codebase follows standard Kotlin style with a
100-column limit. Match the surrounding code.

## Three rules that matter more than style

These exist because each one has already caused a real bug.

### 1. Config writes replace, they don't merge

`set_config` and `set_channel` overwrite the **entire** message on the radio. Building a
fresh `LoRaConfig` from the handful of fields the UI shows will silently reset
`tx_power`, `channel_num`, `override_frequency` and everything else — moving someone's
radio off its frequency slot.

Always start from the radio's own last-sent proto:

```kotlin
val current = store.loraConfig.value ?: error("config not loaded")
val updated = current.toBuilder().setRegion(newRegion).build()
```

The same reasoning is why **channel mute is local to the watch**: we never store the PSK,
so we can't write a channel back without destroying its encryption key.

### 2. One GATT operation at a time

Android's Bluetooth stack tolerates exactly one outstanding operation per connection.
Issuing a second read before the first completes is the classic cause of a silently
stalled BLE link. `GattLink` funnels every operation through a mutex onto a
`CompletableDeferred` — don't bypass it.

Order matters too. `RadioSession.open()` subscribes to `FromNum` *before* requesting
anything, then drains the stale FIFO, then asks for config. Reordering breaks the
handshake in ways that only show up on some radios.

### 3. Cancellation is not an error

`runCatching` catches `CancellationException` like anything else. If you turn that into
user-facing state, a Compose internal message ends up rendered on the watch — which is
exactly what happened in 1.4.1. Rethrow it:

```kotlin
.onFailure { error ->
    if (error is CancellationException) throw error
    // …handle real failures
}
```

Related: don't launch long-running work from `rememberCoroutineScope()` in a composable
that disappears when the state changes. It will cancel its own work.

## Commit messages

Explain *why*, not just what. A one-line subject, then a body describing the problem the
change solves. Look at `git log` for the house style.

## Testing expectations

Pure logic — anything in `mesh/model`, `update/Version`, addressing helpers — should have
unit tests. Look at `app/src/test/` for examples.

Anything touching BLE or real radio behaviour can't be unit tested meaningfully, so say
plainly in your PR what hardware you tested against. "Tested on a Pixel Watch 3 with a
RAK4631" is worth more than any amount of mocking here.

## Reporting bugs

Use the [bug report template](https://github.com/GPTmadeit/Watchtastic/issues/new?template=bug_report.yml).
Watch model, radio model, firmware version and modem preset are all genuinely load-bearing.

## Security

Don't open a public issue for a vulnerability — see [SECURITY.md](SECURITY.md).
